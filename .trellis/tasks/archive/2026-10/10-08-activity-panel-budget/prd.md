# 反馈面板按优先级分配行数

## 背景（已量化）

右下角「反馈 / 请求活动」面板（`src/tui/render.ts` 的 `activityRows` + `panel()`）把三块内容顺序拼成一个数组：
反馈事件（最新在上，`MAX_EVENTS = 4`，每条最多 4 行）→ 空行 → 指标 3 行 → 最近请求（每条 2 行）。
`panel()` 只会 `lines.slice(0, bodyHeight)`，即**从上往下切**。

面板可用内容行数很小：`mainHeight = height - 头部3 - 页脚1 - 1`，守护进程面板固定占 12 行，
所以 24 行终端下反馈面板只有 `24-5-12=7` 行 → 内容 `7-2=5` 行。而 4 条长反馈可达 16 行。

实测（4 条长反馈 + 有指标 + 有最近请求）：

- `height: 24, width: 80`：`近60秒 / 平均耗时 / 本次运行` **三行全部消失**，最近请求也消失，面板只剩事件。
- `height: 30, width: 80`：指标三行出现，但最近请求仍被挤掉。

即「永远该看到的实时指标」被「瞬时反馈」挤没，优先级反了。

## 目标

内容行数按优先级分配，保证：

1. **指标块永远优先**（3 行；无指标时是 4 行空态）。
2. **最新一条反馈保底可见**（≥1 行，空间够时 2 行）。
3. 旧反馈、最近请求用剩余空间；放不下就少显示，但**任何情况下都不得超出面板高度**。

渲染顺序不变（反馈在上、指标在下），只改「分配」不改「顺序」。

## 算法（`B` = 传给 `activityRows` 的 `height`，即面板内容行数）

```
metricRows = metrics ? 3 : 4            // 指标 3 行；无指标时是 4 行空态
hasEvents  = state.events.length > 0
sep        = hasEvents ? 1 : 0          // 事件与指标之间的空行，最先被牺牲

eventBudget = max(B - metricRows - sep, 0)
if (hasEvents && eventBudget === 0 && B - metricRows >= 1) { sep = 0; eventBudget = 1 }

// 事件：最新在上，每条最多 EVENT_LINE_CAP = 2 行；逐条累加直到用满 eventBudget
//       某条被行数截断时，最后一行末尾补 `…`
usedEventRows = min(eventBudget, Σ 每条 min(真实行数, 2))

remaining = B - metricRows - sep - usedEventRows
recentEntries = max(floor(remaining / 2), 0)   // 每条请求 2 行，只放整条
```

- `metricRows` 消耗的 3（或 4）行**绝不让位**；`sep` 是第一个牺牲的，其次是旧事件与最近请求。

**实现时对上面伪码的两处修正（已验证）：**

1. 若 `eventBudget = B - metricRows - sep` 不加约束，事件会吃光共享空间：`height: 30`（`B = 11`）下
   4 条 2 行事件占满 7 行，`recentEntries = 0`，与验收标准「30 行时至少一条最近请求可见」冲突。
   实现增加 `recentReserve`：有指标、有最近请求且 `shared >= 4` 时预留 2 行给最近请求（即
   「最新一条 2 行 + 一条最近请求 2 行」放得下就让位）。
2. 若 `B <= metricRows`，上面的伪码会留下 `sep = 1`，导致首行空白把指标挤出去。实现改为
   仅在 `available >= 2` 时才留 `sep`，`available === 1` 时 `sep = 0` 且 `eventBudget = 1`。
- 事件行数上限从 4 收到 **2**：一条超长错误不再独占面板；被截断时补 `…` 以便和「内容本来就短」区分。
- 旧事件被整个丢弃是**有意的**：面板是「最新状态」而不是完整日志，被丢的旧反馈已被更新的取代。此取舍需写进 spec。

## 改动清单

1. `src/tui/render.ts` `activityRows`：按上述算法重排为「先算预算、再生成各行」；事件行数上限 4 → 2，截断补 `…`。
2. 指标块文案与内容不变（仍是 `近60秒 请求 N · 错误 N` / `平均耗时 Nms` / `本次运行 请求 N · 错误 N`，计数走 `formatCount`）。
3. 无指标空态（4 行）保持现有文案。
4. `.trellis/spec/frontend/interaction-guidelines.md`：在 `反馈 / 请求活动` 那条补上优先级规则与「旧反馈可被丢弃」的取舍。
5. 回归测试。

## 验收标准

- [ ] `height: 24, width: 80`，4 条各占 ≥2 行的反馈事件 + 有指标 + 有最近请求时：`近60秒` / `平均耗时` / `本次运行` **三行全部可见**，且最新一条反馈的首行可见。
- [ ] `height: 30` 同条件下：指标三行可见，且至少一条最近请求条目可见。
- [ ] 单条事件最多渲染 2 行；被行数截断时最后一行以 `…` 结尾。
- [ ] 无反馈事件时，面板内容与改动前等价（指标 + 最近请求），不出现多余空行。
- [ ] 无指标（`暂无请求指标`）空态下同样不超高度，且事件不会把它挤没或反过来。
- [ ] 帧不变量：`width ∈ {72, 80, 90, 100}` × `height ∈ {12, 16, 20, 24, 30, 34}`，每行等宽、末行 `width-1`、总行数 ≤ height；最长反馈 + 最大计数下同样成立。
- [ ] `npm run typecheck` / `npm test` / `npm run build` 全绿；版本仍 `1.2.0`。

## 非目标

- 不改 `src/metrics.ts`、status 载荷字段、统计页、`/v1`。
- 不新增按键、不做面板滚动或展开。
- 不改守护进程面板固定 12 行的策略。（若想给反馈面板更多空间，是另一个话题，不在本次范围。）
