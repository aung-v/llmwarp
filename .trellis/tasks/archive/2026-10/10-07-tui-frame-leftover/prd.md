# TUI 重绘残留：表头没补满宽度导致「处理中…」永挂屏幕

## Goal

TUI 已经不在「处理中」状态时，屏幕上仍然挂着 `处理中…`（以及更早一帧的导航栏提示
`←→ 换页  ↑↓ 进入列表` 的尾巴），用户以为重启没结束。修掉这个「假处理中」。

## Background（根因，已按真实终端回放复现）

`startTui()` 的 `draw()` 是 `ESC[H` + 整帧 + `ESC[J`。`ESC[J`（ED 0）只擦除
「光标当前位置 → 屏幕末尾」，**擦不掉同一行里光标之前的旧字符**。所以只要新帧的某一行
比上一帧的同一行短，旧尾巴就留在屏幕上。

面板行经过 `panel()` 补满宽度，从来不出问题；出问题的是**没补宽度的三行表头与页脚**
（`src/tui/render.ts` 里 `header` 数组与 `footer`）。

复现路径（隔离配置，按键：`←`（焦点到导航栏）→ `↓`（进入列表）→ `→`（到 daemon 面板）
→ `Enter` → `Enter`（确认重启））：

1. 焦点在导航栏：第 2 行 = `[ 模型 ] … [ 统计 ]  ←→ 换页  ↑↓ 进入列表`
2. 进入处理中：第 2 行 = `[ 模型 ] … [ 统计 ]  处理中…`（短 6 列）→ 只盖住 `←→ 换`，
   剩下 `页  ↑↓ 进入列表`
3. 处理中结束：第 2 行 = `[ 模型 ] … [ 统计 ]`（更短）→ 剩下 `处理中…  ↑↓ 进入列表`
   永久挂在屏幕上，直到表头再次变长

重启本身是成功的（daemon 换了 pid、按钮恢复、右下角出现 `✓ 已重启 daemon`），
页脚也回到正常提示——**只有那一行没被重画**，所以这是渲染 bug，不是状态 bug。
（上一轮 `f54350a` 修的 refresh 覆盖竞态是真的，但它不是这个可见症状的原因。）

顺带：表头既不补宽也不截断，窄终端下超宽会换行，把整屏顶歪、错位更严重。

## Requirements

1. `renderTui()` 返回的**每一行**都必须补满/截断到 `width`，帧是固定矩形。
2. 帧的行数不得超过 `height`。`draw()` 写满终端高度就会让终端滚动，整屏错位；
   实测 `确认框 + 左右面板` 在 22/24 行的终端上会渲染出 26–29 行（`activityHeight`
   用 `Math.max(…, 5)` 硬撑出 5 行，`sideBySide` 再取两列的最大值）。修复后反馈面板
   只在剩余高度 ≥3 时出现，并在收尾处兜底：整帧永不超过 `height`（页脚与确认框优先保留）。
3. 不改任何文案、配色、面板布局与行数：修复后同一状态下可见内容应与修复前完全一致，
   差别只在行尾补齐的空格。
4. 不改 `draw()` 的 `ESC[H` / `ESC[J` 协议（补满宽度后它已经足够）。

## Acceptance Criteria

- [ ] `renderTui(state, { height, width })` 的每一行 `visibleWidth(line) === width`
      （含表头、页脚、确认面板、统计页）。
- [ ] 回归测试：模拟「导航栏提示 → 处理中 → 结束」两次渲染，断言后一帧每一行都不短于
      `width`，即不会留下上一帧的尾巴；并断言 `处理中…` 只出现在切换态。
- [ ] 回归测试：`处理中` / `切换确认框` / `导航栏提示` 等状态在 `height` 22/24/30 下
      `renderTui()` 的行数都不超过 `height`（截图里确认框弹出时曾在 24 行终端上输出 26 行）。
- [ ] 回归测试：窄终端（如 `width: 72`）下表头不超宽（`visibleWidth ≤ width`），不换行。
- [ ] `.trellis/spec/frontend/interaction-guidelines.md`（或 state-management）写明：
      整帧重绘依赖「每行等宽」，任何新增的行都必须补满宽度，否则 `ESC[J` 擦不掉残留。
- [ ] `npm run typecheck` / `npm run build` / `npm test` 全绿；版本号仍为 `1.1.0`。

## 明确不做

- 不改成 `ESC[2J` 全屏清屏（会闪屏）。
- 不引入行级差分渲染 / 双缓冲。
- 不动 `draw()` 之外的重绘时序（上一轮已修）。
