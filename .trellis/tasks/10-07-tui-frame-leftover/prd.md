# TUI 重绘残留：表头没补满宽度导致「处理中…」永挂屏幕

## Goal

TUI 已经不在「处理中」状态时，屏幕上仍然挂着 `处理中…`（以及更早一帧的导航栏提示
`←→ 换页  ↑↓ 进入列表` 的尾巴），用户以为重启没结束。修掉这个「假处理中」。

## Background（根因，已按真实终端回放复现）

`startTui()` 的 `draw()` 是 `ESC[H` + 整帧 + `ESC[J`。`ESC[J`（ED 0）只擦除
「光标当前位置 → 屏幕末尾」，**擦不掉同一行里光标之前的旧字符**。所以只要新帧的某一行
比上一帧的同一行短，旧尾巴就留在屏幕上。

面板行经过 `panel()` 补满宽度，从来不出问题；出问题的是**没补宽度的三行表头与页脚**
（`src/tui/render.ts` 里 `header` 数组与 `footer`）。

复现路径（隔离配置，按键：`←`（焦点到导航栏）→ `↓`（进入列表）→ `→`（到 daemon 面板）
→ `Enter` → `Enter`（确认重启））：

1. 焦点在导航栏：第 2 行 = `[ 模型 ] … [ 统计 ]  ←→ 换页  ↑↓ 进入列表`
2. 进入处理中：第 2 行 = `[ 模型 ] … [ 统计 ]  处理中…`（短 6 列）→ 只盖住 `←→ 换`，
   剩下 `页  ↑↓ 进入列表`
3. 处理中结束：第 2 行 = `[ 模型 ] … [ 统计 ]`（更短）→ 剩下 `处理中…  ↑↓ 进入列表`
   永久挂在屏幕上，直到表头再次变长

重启本身是成功的（daemon 换了 pid、按钮恢复、右下角出现 `✓ 已重启 daemon`），
页脚也回到正常提示——**只有那一行没被重画**，所以这是渲染 bug，不是状态 bug。
（上一轮 `f54350a` 修的 refresh 覆盖竞态是真的，但它不是这个可见症状的原因。）

顺带：表头既不补宽也不截断，窄终端下超宽会换行，把整屏顶歪、错位更严重。

## Requirements

1. `renderTui()` 返回的**每一行**都必须补满/截断到 `width`，帧是固定矩形。
2. 帧的行数不得超过 `height`。`draw()` 写满终端高度就会让终端滚动，整屏错位；
   实测 `确认框 + 左右面板` 在 22/24 行的终端上会渲染出 26–29 行（`activityHeight`
   用 `Math.max(…, 5)` 硬撑出 5 行，`sideBySide` 再取两列的最大值）。修复后反馈面板
   只在剩余高度 ≥3 时出现，并在收尾处兜底：整帧永不超过 `height`（页脚与确认框优先保留）。
3. 不改任何文案、配色、面板布局与行数：修复后同一状态下可见内容应与修复前完全一致，
   差别只在行尾补齐的空格。
4. 不改 `draw()` 的 `ESC[H` / `ESC[J` 协议（补满宽度后它已经足够）。

## Acceptance Criteria

- [ ] `renderTui(state, { height, width })` 的每一行 `visibleWidth(line) === width`
      （含表头、页脚、确认面板、统计页）。
- [ ] 回归测试：模拟「导航栏提示 → 处理中 → 结束」两次渲染，断言后一帧每一行都不短于
      `width`，即不会留下上一帧的尾巴；并断言 `处理中…` 只出现在切换态。
- [ ] 回归测试：`处理中` / `切换确认框` / `导航栏提示` 等状态在 `height` 22/24/30 下
      `renderTui()` 的行数都不超过 `height`（截图里确认框弹出时曾在 24 行终端上输出 26 行）。
- [ ] 回归测试：窄终端（如 `width: 72`）下表头不超宽（`visibleWidth ≤ width`），不换行。
- [ ] `.trellis/spec/frontend/interaction-guidelines.md`（或 state-management）写明：
      整帧重绘依赖「每行等宽」，任何新增的行都必须补满宽度，否则 `ESC[J` 擦不掉残留。
- [ ] `npm run typecheck` / `npm run build` / `npm test` 全绿；版本号仍为 `1.1.0`。

## 明确不做

- 不改成 `ESC[2J` 全屏清屏（会闪屏）。
- 不引入行级差分渲染 / 双缓冲。
- 不动 `draw()` 之外的重绘时序（上一轮已修）。

## 第二轮续修（2026-10-07，重开后）

第一轮的修复（`224bad8` 补宽 / 不超高，`741da3d` 末行只补到 `width - 1`）在合成回放下
「0 滚屏」，但用户真机复测仍然重现 **导航栏叠了两层**：

```
⚡ llmwarp TUI   ● 运行中  显式切换，不影响代理服务
                        模型 ] [ 路由 ] [ 供应商 ] [ 统计 ]  处理中…
[ 模型 ] [ 路由 ] [ 供应商 ] [ 统计 ]  ←→ 换页  ↑↓ 进入列表
```

第 1 行尾巴上挂着旧内容，第 2 行是「处理中」那帧的导航栏且丢了开头两列，第 3 行才是
当前帧的导航栏 —— 典型的**整帧纵向错位一格 + 横向串列**，即上一轮没覆盖的第三支。

### 真根因

`draw()` 是 `ESC[H` + 整帧 + `ESC[J`，帧内靠 `"\n"` 换行。`"\n"` 会不会回到第 1 列
取决于终端的 OPOST/ONLCR（Node 的 raw 模式在 Unix 上正好会把它清掉）：

- 不回列时，`\n` 只下移一行、列号不变；而每行都被补满 `width`，光标正停在第 `width`
  列，于是**下一行就从上一行结尾那一列继续写**，屏幕上叠出第二层导航栏。
- 再叠加上一轮的滚屏敏感（帧恰好写满终端高度时终端滚动），纵向也错位一格。

即：`ESC[H + 帧 + ESC[J` 这套协议本身依赖了三件不确定的事 —— 换行回不回列、补宽对不对、
终端会不会在底部滚动。只要其中一件和预期不符，整屏就错位。

### 第二轮修复

1. 新增 `frameToAnsi()`（`src/tui/render.ts`）：每行用 CSI 绝对定位
   `ESC[<row>;1H` 写在第 row 行第 1 列，行尾 `ESC[K` 擦掉该行剩余列，帧尾 `ESC[J`
   擦掉屏幕剩余部分。输出里**一个裸换行都没有**，完全不依赖 `\n` 语义；任何一行写歪，
   下一行的绝对定位都会把它拉回来。
2. `draw()` 把帧高限制为 `rows - 1`（`src/tui/index.ts`）：帧永远不落在终端最后一行，
   任何回绕都不可能触发滚屏；末行仍然只补到 `width - 1`，不写右下角那一格。
3. `renderTui()` 收尾加硬裁：`...slice(0, height)`，极端矮终端 + 多行确认框时也不再超高。

因此 AC 第 4 条「不改 `draw()` 的 `ESC[H` / `ESC[J` 协议」被本次修复**作废**（正是这套
协议不可靠），其余 AC 继续有效，并补上第二轮验收：

- [x] `frameToAnsi(frame)` 输出不含裸换行，且每行都由 `ESC[<row>;1H` 绝对定位。
- [x] pty 真机字节流在「延迟回绕」和「立即回绕」两种终端模型下重放，`滚屏 0 次`，
      最终屏只有一条导航栏（120×24 / 120×30 均验证）。
- [x] 走完整套重启（确认 → 启动 daemon）：「处理中」不残留，右下角出现 `✓ 已启动 daemon`。
- [x] `.trellis/spec/frontend/interaction-guidelines.md` 同步改为「绝对定位 + 帧不占最后
      一行」的新契约。

### 为什么第一轮会误判（break-loop）

- **根因分类**：E 隐式假设 —— 代码默认「`\n` 会回到第 1 列」，而这取决于终端 termios。
- **第一轮为什么失败**：Scope 不全。只覆盖了「同一行内旧尾巴」和「帧超高的滚动」，
  没覆盖「换行不回列导致的横向串写」；而且用合成回放（自己写的终端模型）
  代替真机验证，模型里恰好让 `\n` 回列了，于是「0 滚屏」被当成了修好。
- **防复发**：帧输出协议层面消除对 `\n`/滚屏/补宽的依赖（绝对定位），并在 spec 里
  把「帧怎么写」写成契约；今后 TUI 渲染类改动必须在一台真终端里肉眼确认，
  合成回放只能作为补充证据，不能单独作为验收依据。
