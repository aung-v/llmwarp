# TUI 显式确认后重启 daemon

## 目标

在常驻 TUI 里提供一个"把焦点移到守护进程信息栏的按钮、选中并显式确认后才重启本地 daemon"的能力，免去退出 TUI 再用 CLI 执行 `llmwarp stop && llmwarp start`。

## 背景

- TUI 是独立客户端进程（`llmwarp tui`），当前只通过管理 API 读写：`GET /_llmwarp/status`、`POST /_llmwarp/use`。
- `src/daemon.ts` 已导出 `stopDaemon()` / `startDaemon()`，CLI 的 `llmwarp stop` / `llmwarp start` 用的就是这套。`startDaemon()` 已处理端口占用、残留 llwarp 进程清理、`waitForDaemon()` 就绪确认（`src/daemon.ts:79`）。
- 现有 `POST /_llmwarp/reload` 只重读配置（`src/server.ts:26`），无法改变已绑定的监听端口（`src/server.ts:205`）；改配置里的 `port` 必须重启。daemon 卡死时也只能靠外部 kill。
- `09-27-persistent-tui` 的 PRD/design 把"重启 daemon"列为非目标。本任务是对该范围的有意修订。
- 依赖 `09-29-tui-use-persist`：否则"重启后刚切的模型被还原"会立刻暴露，体验突兀。

## 交互模型（本次修订，覆盖旧版按键方案）

用户明确要求：快捷键只服务基础操作，动作类功能靠导航选中后再确认；重启、路由切换不在同一层级。

```
┌─ llmwarp TUI ── ● 运行中 ──────────────────────────────┐
│ [ 模型 ]  [ 路由 ]            │ 守护进程                │
│                               │  端口 / 版本 / 启动时间  │
│  模型列表 / 路由列表           │  ┌───────────────────┐  │
│  ↑↓ 选择  Enter 确认           │  │  重启 daemon       │  │
│                               │  └───────────────────┘  │
│                               │ 请求活动                 │
└───────────────────────────────┴─────────────────────────┘
```

- 顶部导航栏只有两项：`模型`、`路由`；**没有**独立的"重启"导航项。
- `模型`页 = 现有模型列表：`↑↓` 选，`Enter` 切换。
- `路由`页 = 路由模式列表（`按客户端请求` / `统一用当前模型`）：`↑↓` 选，`Enter` 切换；不再有 `m`。
- `重启 daemon` 是右侧"守护进程"信息栏里的一个按钮，不占导航栏。
- 导航：`↑↓` 在当前区域内选择；`←→` 在左栏（导航栏+列表）与右栏（守护进程）之间移动焦点，焦点在导航栏行时 `←→` 用于切换 `模型`/`路由` 页。
- `Enter` 触发当前选中项；切换模型、切换路由、重启 daemon 都要二次确认，`Enter` 确认、`Esc` 取消。
- 允许的全局基础按键：方向键、`Enter`、`Esc`、`r`（刷新）、`q`（退出）、`Ctrl-C`。**不允许"随便按一个键就重启"。**

## 方案（A：TUI 进程直接调用现成的生命周期函数）

在守护进程信息栏里选中"重启 daemon"按钮并按 `Enter` → 进入确认态 → 用户确认 → TUI 进程依次执行：

1. `stopDaemon()`（读 `daemon.json` 拿 pid，发 SIGTERM，清理 `daemon.json`）
2. `startDaemon(getPort(loadConfig()))`（spawn 新 daemon，轮询到就绪）
3. `refresh()` 刷新界面

不新增 daemon 端自重启端点（B 方案），理由是 A 代码更少，且 daemon 卡死（不响应 HTTP）时仍能救回来。

## 需求

- 新增顶部导航栏（`模型` / `路由`），右侧保留守护进程信息栏与请求活动。
- 路由模式切换迁到 `路由`页的列表里，移除 `m` 快捷键。
- 在守护进程信息栏里新增"重启 daemon"按钮。**不存在任何直接触发重启的按键**；必须把焦点移到该按钮并选中。
- 选中"重启 daemon"并按 `Enter` 后进入确认态；确认文案必须写明代价：重启会中断进行中的 `/v1` 请求。
- 确认态用 `Enter` 确认、`Esc` 取消；取消不触发任何操作。
- 确认后：停止当前 daemon → 启动新 daemon → 刷新状态。
- 复用 `src/daemon.ts` 的 `stopDaemon()` / `startDaemon()`，不新增进程管理逻辑。
- daemon 未运行时选中该按钮：退化为"启动"，或明确提示后启动，不静默失败。
- 重启失败（`startDaemon()` 抛错）：显示错误，TUI 不退出，保持可用。
- 重启期间禁用其他操作（焦点与按钮不可用），避免与切换/刷新并发。
- 重启后新 daemon 的 token/pid 必须能被后续请求正确读取（`adminRequest()` 每次重读 `daemon.json`，`src/daemon.ts:112`）。
- 保持进程边界：daemon 由 `startDaemon()` spawn（`detached` + `unref`），TUI 退出或被 kill 不影响 daemon。

## 非目标

- 不新增 daemon 端自重启管理端点（B 方案）。
- 不把 daemon 生命周期的所有权交给 TUI；TUI 只发起显式请求。
- 不新增任何单字母动作快捷键。
- 不改 `/v1` 代理逻辑，不引入新依赖。

## TUI 设计要求

- 沿用现有交互语言：`src/ui.ts` 的 `ok`/`warn`/`fail`/`info`/`hint`/`dim`/`bold` 与 `✓`/`!`/`✗` 标记。
- 焦点与选中态必须可见：导航栏要标出当前页，列表和"重启 daemon"按钮都要能区分"已选中"与"未选中/未聚焦"。
- 焦点只用方向键切换；两步确认用基础键：`Enter` 确认、`Esc` 取消。
- 键位提示必须更新并放在操作说明区；用户可见文案保持中文。
- 输出前对来自配置和 daemon 状态的文本做 ANSI 转义；不显示 token 或 API key。
- 确认态需要能区分"切换模型""切换路由""重启 daemon"等意图（当前 `TuiState.confirming` 只是单层枚举，需扩展）。

## 验收标准

- [ ] 顶部导航栏有 `模型` / `路由` 两项，可切换页面。
- [ ] 路由模式在 `路由`页的列表里选择切换；`m` 快捷键已移除。
- [ ] 守护进程信息栏里有"重启 daemon"按钮；不存在任何"按单个键直接重启"的路径。
- [ ] 必须把焦点移到按钮并 `Enter` 才能进入重启确认。
- [ ] 全局按键只有方向键 / `Enter` / `Esc` / `r`（刷新）/ `q`（退出）/ `Ctrl-C`，无单字母动作键（`m` 已移除）。
- [ ] `Enter` 进入重启确认态；`Esc` 取消不触发任何操作。
- [ ] 确认文案包含"中断 `/v1` 请求"的提示。
- [ ] daemon 未运行时选中按钮行为明确（启动或提示），不静默失败。
- [ ] 确认后 daemon 以新 pid 重新运行，TUI 状态刷新且后续切换仍可用（新 token 生效）。
- [ ] 重启失败时 TUI 不退出、不残留半重启状态，错误可见。
- [ ] 重启后 TUI 之前切换的 model 仍生效（依赖 `09-29-tui-use-persist`）。
- [ ] 退出 TUI 后 daemon 继续运行。
- [ ] `npm run typecheck`、`npm test`、`npm run build` 通过。

## 实现决策

- daemon 未运行时，按钮文案切为"启动 daemon"，`Enter` 确认后走 `startDaemon()`（实现后可按手感调整）。
